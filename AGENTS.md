# Blog Platform

A technical blog: Go API, Postgres, and a Next.js frontend. Posts are authored as markdown and imported into Postgres. The first slice is posts plus Postgres full-text search; fuzzy search, Elasticsearch, and pgvector come later.

The goals include learning Postgres internals and search, so some work is deliberately hand-written (see "Working modes").

## Stack

- Go module `github.com/elmerred09/blog`. HTTP via `gin` (kept inside `internal/httpapi`), `log/slog`, `pgx/v5` (`pgxpool`).
- Postgres, with `sqlc` (SQL to Go) and `goose` (migrations).
- `goldmark` + `chroma` for markdown rendering.
- Next.js App Router in `web/`.
- Integration tests use `testcontainers-go` against a real Postgres, not mocks.

## Layout

- `cmd/api` is the HTTP server. `cmd/blogctl` is the CLI (import markdown, reindex).
- `internal/` is grouped by domain: `content/` (markdown-file ingestion: frontmatter, path resolution, the import transaction; only `cmd/blogctl` imports it, enforced by depguard), `render/` (goldmark + chroma markdown to HTML, and the highlighting stylesheet), `slug/` (making and validating slugs), `tags/` (tag and post-tag link writes, run in the caller's transaction), `post/` (the read side the API uses), `admin/` (the editor's write side: create, update, list, preview), `search/` (a `Searcher` interface with a Postgres implementation, so Elasticsearch can be swapped in later), `httpapi/`, `config/`, `platform/db/`.
- `internal/db/` is **generated by sqlc. Never edit it.**
- `api/openapi.yaml` is the HTTP contract. Change it together with the handlers: `internal/httpapi` tests validate every response against it and fail if a route is missing from it.
- `db/migrations/` holds goose migrations. `db/queries/` holds sqlc query files.
- `content/` holds markdown posts with frontmatter (the authoring source of truth).
- `web/` is the Next.js app: `app/` holds the routes (posts list at `/`, a post at `/posts/[slug]`, plus `error.tsx`, `loading.tsx`, `not-found.tsx`), `components/` the small presentational components with their Vitest tests, `lib/api/` the typed API client (the only code that calls the Go API, and where caching lives), `lib/format.ts` display helpers. `web/lib/api/schema.d.ts` is **generated from `api/openapi.yaml` by `make web-types`. Never edit it.** `web/app/chroma.css` (code highlighting colors) is **generated by `make chroma-css`. Never edit it.** `web/AGENTS.md` is written by `next dev`; read it before writing Next.js code.

Not everything above exists yet. Check the tree before assuming a package is there.

## Commands

Run everything through `make`; the Makefile sets up `PATH` for the Go tools.

- `make fmt` / `make fmt-check`: gofmt (`FILES="a.go b.go"` to limit).
- `make lint`: golangci-lint (config in `.golangci.yml`).
- `make test`: `go test -race ./...`.
- `make deps-check`: fail if `go.mod`/`go.sum` aren't tidy (`go mod tidy -diff`, `go mod verify`).
- `make hooks`: install the git hooks (once per clone).
- `sqlc`, `goose`, and `lefthook` are pinned in `go.mod`; run them via `go tool <name>`, not from `~/go/bin`.
- `make sqlc` / `make sqlc-check`: regenerate / verify sqlc output. They skip until `sqlc.yaml` exists.

- `make up` / `make down`: start / stop the compose Postgres. `make migrate` applies migrations to it.
- `make api`: run the API against the compose database (`HTTP_ADDR` defaults to `:8080`).
- `make import POSTS="content/a.md content/"`: import markdown posts with `blogctl`.
- `make chroma-css` / `make chroma-css-check`: regenerate / verify `web/app/chroma.css` with `blogctl css`. The themes are constants in `internal/render/render.go`; rendered HTML only carries class names, so a theme change needs this, not a re-import.

Both binaries require `DATABASE_URL`; the `make` targets set it to the compose database.

- Node comes from nvm, at the major version in `web/.nvmrc`. The Makefile puts that install first on `PATH`, because nvm only loads in interactive shells. `make node-check` confirms `node` and `npm` resolve there.
- `make web-install`: `npm ci` in `web/`. The other web targets fail with a reminder if `node_modules` is missing or older than `package-lock.json`.
- `make web`: Next.js dev server, pointed at `make api` via `API_URL` (default `http://localhost:8080`). `make web-build`: production build.
- `make web-lint` (ESLint), `make web-typecheck` (`tsc --noEmit`), `make web-test` (Vitest).
- `make web-fmt` / `make web-fmt-check`: Prettier (`WEB_FILES="app/page.tsx"` to limit).
- `make web-types` / `make web-types-check`: regenerate / verify the TypeScript API types from `api/openapi.yaml`.
- `make web-check`: all the web checks above, in one target.

Before finishing a change, `make lint` and `make test` should pass. For changes under `web/` or to `api/openapi.yaml`, `make web-check` should pass too.

## Conventions

Scoped rules live in `.cursor/rules/` (`go.mdc`, `sql.mdc`, `web.mdc`). Key points:

- Wrap errors with `%w`, pass `context.Context` first, no global state, table-driven tests.
- Migrations are append-only. Every query needs an index justification. Use keyset pagination on `(published_at, id)`, never `OFFSET`.
- Next.js: server components by default, typed API client.
- Schema changes go through a new migration, then `make sqlc`.

## Automation you should know about

- After you edit a Go file, a hook runs `gofmt` on it. After edits under `db/queries` or `db/migrations`, it runs `make sqlc`. After you edit a file under `web/`, it runs Prettier on it. After you edit `api/openapi.yaml`, it runs `make web-types`.
- When you stop, a hook runs `make lint` and asks you to continue if it reports issues. It doesn't run the web checks.
- Git hooks (lefthook) run lint (which includes the gofmt check), `sqlc diff` and `make chroma-css-check` on commit, and tests on push. For `web/` and `api/openapi.yaml`, they run the web lint, typecheck, Prettier check and API types check on commit (each only when matching files are staged), and `make web-test` on push.

- CI (`.github/workflows/ci.yml`, GitHub Actions) runs on pull requests and pushes to `main`, calling the same `make` targets. The `go` job runs `fmt-check`, `lint` (golangci-lint v2.14.0, built from source with the repo's Go), `sqlc-check`, `chroma-css-check`, `deps-check` and `test` (Docker for the testcontainers tests). The `web` job runs `web-install`, `web-check` and `web-build`. Unlike the stop hook, CI runs the web checks. It doesn't use nvm, so don't call `make node-check` there. Keep the golangci-lint version in the workflow in step with the one you use locally.

## Working modes

- **Human writes, agent reviews and teaches:** SQL, search ranking, and Postgres tuning. Explain, critique, or quiz; don't generate the implementation unless asked.
- **Agent writes, human reviews:** boilerplate such as Next.js scaffolding, CI YAML, Makefile, Docker config.
- For a new feature: plan first, write tests, then implement.
