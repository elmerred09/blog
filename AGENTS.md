# Blog Platform

A technical blog: Go API, Postgres, and a Next.js frontend. Posts are written in the admin editor, which saves them to Postgres as markdown plus rendered HTML; the database is the source of truth. The first slice is posts plus Postgres full-text search; fuzzy search, Elasticsearch, and pgvector come later.

The goals include learning Postgres internals and search, so some work is deliberately hand-written (see "Working modes").

## Stack

- Go module `github.com/elmerred09/blog`. HTTP via `gin` (kept inside `internal/httpapi`), `log/slog`, `pgx/v5` (`pgxpool`).
- Postgres, with `sqlc` (SQL to Go) and `goose` (migrations).
- `goldmark` + `chroma` for markdown rendering.
- Next.js App Router in `web/`.
- Integration tests use `testcontainers-go` against a real Postgres, not mocks.

## Layout

- `cmd/api` is the HTTP server. `cmd/blogctl` is a small CLI; its one command, `css`, writes the highlighting stylesheet.
- `internal/` is grouped by domain: `render/` (goldmark + chroma markdown to HTML, and the highlighting stylesheet), `slug/` (making and validating slugs), `tags/` (tag and post-tag link writes, run in the caller's transaction, and `Store` for the public and admin tag lists; the public-visibility rule lives in its query), `post/` (the read side the API uses), `admin/` (the editor's write side: create, update, list, preview), `media/` (presigned image uploads to S3-compatible storage), `search/` (a `Searcher` interface with a Postgres implementation, so Elasticsearch can be swapped in later), `validation/` (the one error type for rejected input: a list of field problems that `httpapi` maps to a 400 in `writeInvalid`; new write packages return it rather than defining their own), `httpapi/`, `config/`, `platform/db/`, `platform/telemetry/` (OpenTelemetry traces and logs for the API; no-op unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set).
- `internal/db/` is **generated by sqlc. Never edit it.**
- `api/openapi.yaml` is the HTTP contract. Change it together with the handlers: `internal/httpapi` tests validate every response against it and fail if a route is missing from it.
- `db/migrations/` holds goose migrations. `db/queries/` holds sqlc query files.
- `db/seed/` holds data for `make seed`: `posts-tags.sql` (10k synthetic posts with skewed tags, for query-plan work).
- `web/` is the Next.js app: `app/` holds the routes (posts list at `/`, a post at `/posts/[slug]`, `sitemap.ts`, `robots.ts`, Open Graph images, plus `error.tsx`, `loading.tsx`, `not-found.tsx`), `components/` the small presentational components with their Vitest tests, `lib/api/` the typed API client (the only code that calls the Go API, and where caching lives), `lib/format.ts` display helpers. Admin sign-in is Better Auth (GitHub only, stateless: the session is an encrypted cookie, with no database): `lib/auth/` holds its config and the GitHub-id allowlist, `app/api/auth/[...all]` its endpoints, `app/sign-in` the page and the sign-in and sign-out actions, and `lib/admin/session.ts` has `requireAdmin()`, the one place that reads the session. Every page under `app/admin` and every admin server action calls it; `proxy.ts` only redirects requests that have no session cookie. `lib/api/admin.ts` is the admin API client: uncached, it signs a two-minute EdDSA token per call (`lib/api/token.ts`) for the `Admin` that `requireAdmin()` returned, and returns expected failures (validation problems, `conflict`, `slug_taken`, `not_found`, `too_large`) as values. `app/admin/actions.ts` holds the editor's server actions (`savePost`, `previewPost`, `createImageUpload`); `savePost` expires the `posts` tag and the post's page under its new and old slug. The admin pages are the post list (`app/admin/page.tsx`) and the editor (`app/admin/posts/new`, `app/admin/posts/[id]`). The editor's client components live in `components/admin/` (`PostEditor` form, Tiptap `Editor` with its toolbar, `TagInput`, `PublishControls`), loaded client-only through `post-editor-loader.tsx`; their logic lives in `lib/admin/` (the Tiptap extension set, slug suggestion, publish-time rules, browser upload). `components/post-body.tsx` renders `body_html` for both the public post page and the preview. `web/lib/api/schema.d.ts` is **generated from `api/openapi.yaml` by `make web-types`. Never edit it.** `web/app/chroma.css` (code highlighting colors) is **generated by `make chroma-css`. Never edit it.** `web/AGENTS.md` is written by `next dev`; read it before writing Next.js code.
- `web/e2e/` is the Playwright suite (`make e2e`), run against the real stack. `web/playwright.config.ts` starts the API on `:8081` and the standalone Next server on `:3100` with the env in the gitignored `e2e/.env.e2e` (fresh test keys from `scripts/e2e-env.sh`; `e2e/env.ts` reads it and fails if `web/.env.local` sets a key it doesn't override). Its projects run in order: `fixtures` creates the posts in `fixtures.ts` through the admin API, `auth` mints a Better Auth session cookie (`auth.ts`, which copies better-auth 1.7.10's cookie format; the setup fails with a clear message if an upgrade changes it) and saves it as the admin storageState, then the `public` (`public.spec.ts`, `search.spec.ts`, `seo.spec.ts`) and `admin` (`admin-*.spec.ts`) specs. Rules for specs:
  - Nothing may request a public page before the `fixtures` project runs: the list and search are `"use cache"`, and posts created through the API don't expire them.
  - Admin specs import `test` from `e2e/admin.ts` (it fails on uncaught browser errors and hydration warnings), write their own posts under `uniqueSlug`, and read only those. Public specs assert on fixture posts and their relative order, never on counts or positions.
  - Assert on the final URL and on visible text, never on status codes: redirects from `requireAdmin()` and not-found pages are streamed with a 200.
  - Only the search fixtures, the draft and the scheduled post contain "quokka"; the search spec counts on that.
- `deploy/` is production. `deploy/docker/` builds the API image, the goose image, and the Next.js standalone image. `deploy/prod/` is the droplet stack: Compose, Caddy, env examples, and the backup script.

Not everything above exists yet. Check the tree before assuming a package is there.

## Commands

Run everything through `make`; the Makefile sets up `PATH` for the Go tools.

- `make fmt` / `make fmt-check`: gofmt (`FILES="a.go b.go"` to limit).
- `make lint`: golangci-lint (config in `.golangci.yml`).
- `make test`: `go test -race ./...`.
- `make deps-check`: fail if `go.mod`/`go.sum` aren't tidy (`go mod tidy -diff`, `go mod verify`).
- `make hooks`: install the git hooks (once per clone).
- `sqlc`, `goose`, and `lefthook` are pinned in `go.mod`; run them via `go tool <name>`, not from `~/go/bin`.
- `make sqlc` / `make sqlc-check`: regenerate / verify sqlc output. They skip until `sqlc.yaml` exists.

- `make up` / `make down`: start / stop the compose Postgres and RustFS (the local S3 stand-in; `rustfs-init` creates the bucket). The local S3 credentials, bucket and region live only in `deploy/rustfs/local.env`, which compose and `scripts/admin-keys.sh` both read. `make migrate` applies migrations to Postgres (`migrate-down`, `migrate-status`, `migrate-new NAME=...` too); every database target takes `GOOSE_DBSTRING=...` to point at another database.
- `make otel-up` / `make otel-down`: start / stop the local trace and log stack (`grafana/otel-lgtm` on the `observability` compose profile; Grafana at http://localhost:3001, login admin/admin). `make up` does not start it. `OTEL=1 make api` and `OTEL=1 make web` export to it (`OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318`). With that variable unset, the API and Next export nothing, which is how tests, CI, and E2E run. `NEXT_OTEL_VERBOSE=1` shows the spans Next hides by default. In Grafana, Explore with Tempo, then "Logs for this span" for the matching Loki lines.
- `make api`: run the API against the compose database (`HTTP_ADDR` defaults to `:8080`). It sources `.env` when that file exists.
- `make admin-keys ADMIN_GITHUB_ID=<id>`: write a gitignored `.env` (API public key, `ADMIN_SUBJECTS`, local S3 settings) and `web/.env.local` (the same id as `ADMIN_GITHUB_IDS`, the private key, a fresh `BETTER_AUTH_SECRET`, and empty `GITHUB_CLIENT_ID`/`GITHUB_CLIENT_SECRET` to fill in from a GitHub OAuth app with callback `http://localhost:3000/api/auth/callback/github`), via `scripts/admin-keys.sh`. Refuses to overwrite either file. Admin sign-in is all or nothing (including `ADMIN_JWT_PRIVATE_KEY`): with none of its variables set, `/admin` is a 404; with some, it fails naming the rest.
- `make seed`: replace every post and tag in the compose database with `db/seed/posts-tags.sql` (`SEED=<name>` picks another file in `db/seed/`). A fresh clone runs `make up`, `make migrate`, `make seed`.
- `make chroma-css` / `make chroma-css-check`: regenerate / verify `web/app/chroma.css` with `blogctl css`. The themes are constants in `internal/render/render.go`; rendered HTML only carries class names, so a theme change needs this, not re-rendering posts.

The API requires `DATABASE_URL`; `make api` sets it to the compose database.

- Node comes from nvm, at the major version in `web/.nvmrc`. The Makefile puts that install first on `PATH`, because nvm only loads in interactive shells. `make node-check` confirms `node` and `npm` resolve there.
- `make web-install`: `npm ci` in `web/`. The other web targets fail with a reminder if `node_modules` is missing or older than `package-lock.json`.
- `make web`: Next.js dev server, pointed at `make api` via `API_URL` (default `http://localhost:8080`). Next loads `web/.env.local` itself; don't source it in the shell, or the private key reaches Next with literal `\n`. `SITE_URL` (default `http://localhost:3000`) is passed too: Next bakes it into prerendered metadata, the sitemap, and `robots.txt`, so a production build needs the real domain at **build** time, not only at runtime. `SITE_INDEXING=true` is the only value that lets `robots.txt` allow crawling; leave it unset everywhere except the production deploy. `make web-build`: production build. It does not need the Go API. The public routes are `/sitemap.xml`, `/robots.txt`, and the Open Graph images at `/opengraph-image` and `/posts/<slug>/opengraph-image`.
- `make web-lint` (ESLint), `make web-typecheck` (`tsc --noEmit`), `make web-test` (Vitest).
- `make web-fmt` / `make web-fmt-check`: Prettier (`WEB_FILES="app/page.tsx"` to limit).
- `make web-types` / `make web-types-check`: regenerate / verify the TypeScript API types from `api/openapi.yaml`.
- `make web-check`: all the web checks above, in one target.
- `make e2e`: the Playwright suite. It needs `make up`, and `make e2e-install` (Chromium) once. It recreates the `blog_e2e` database (`make e2e-db`), writes fresh test keys, then runs Playwright, which starts its own API and standalone Next server on `:8081` and `:3100`, so a dev stack on `:8080` and `:3000` keeps running. `E2E_ARGS="admin-editor --headed"` passes arguments to `playwright test`; `make e2e-ui` opens UI mode. On Ubuntu 20.04, which Playwright doesn't support, install with `PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu22.04-x64 make e2e-install`. After changing `deploy/rustfs/cors.json`, apply it with `docker compose run --rm rustfs-init`. E2E isn't part of `web-check` or the git hooks (too slow); CI runs it.

Before finishing a change, `make lint` and `make test` should pass. For changes under `web/` or to `api/openapi.yaml`, `make web-check` should pass too, and `make e2e` for changes to the editor, admin sign-in, caching or the public pages.

## Conventions

Scoped rules live in `.cursor/rules/` (`go.mdc`, `sql.mdc`, `web.mdc`). Key points:

- Wrap errors with `%w`, pass `context.Context` first, no global state, table-driven tests.
- Migrations are append-only. Every query needs an index justification. Use keyset pagination on `(published_at, id)`, never `OFFSET`.
- Next.js: server components by default, typed API client.
- Schema changes go through a new migration, then `make sqlc`.

## Automation you should know about

- After you edit a Go file, a hook runs `gofmt` on it. After edits under `db/queries` or `db/migrations`, it runs `make sqlc`. After you edit a file under `web/`, it runs Prettier on it. After you edit `api/openapi.yaml`, it runs `make web-types`.
- When you stop, a hook runs `make lint` and asks you to continue if it reports issues. It doesn't run the web checks.
- Git hooks (lefthook) run lint (which includes the gofmt check), `sqlc diff` and `make chroma-css-check` on commit, and tests on push. For `web/` and `api/openapi.yaml`, they run the web lint, typecheck, Prettier check and API types check on commit (each only when matching files are staged), and `make web-test` on push.

- CI (`.github/workflows/ci.yml`, GitHub Actions) runs on pull requests and pushes to `main`, calling the same `make` targets. The `go` job runs `fmt-check`, `lint` (golangci-lint v2.14.0, built from source with the repo's Go), `sqlc-check`, `chroma-css-check`, `deps-check` and `test` (Docker for the testcontainers tests). The `web` job runs `web-install`, `web-check` and `web-build`. The `e2e` job starts the compose Postgres and RustFS, caches Playwright's browsers by version, runs `make e2e-install` and `make e2e`, and uploads the report and traces when it fails. Unlike the stop hook, CI runs the web checks. It doesn't use nvm, so don't call `make node-check` there. Keep the golangci-lint version in the workflow in step with the one you use locally.

## Deployment

Production is one DigitalOcean droplet. Docker Compose in `/srv/blog` runs Caddy, Next.js, the Go API, and Postgres. Caddy is the only published port. The API and Postgres stay on the Compose network. Cloudflare proxies the domain and terminates the public certificate. Caddy serves a Cloudflare origin certificate from `/srv/blog/certs/origin.pem` and `origin.key` (mode 600). Create that certificate under SSL/TLS, Origin Server, and include the apex domain and `www`. Images live in the public R2 bucket `blog-media`, served at `media.<domain>`. Database dumps go to the private bucket `blog-backups`.

Secrets stay on the droplet, mode 600, owned by `deploy`. They are not in git.

- `/srv/blog/api.env` is the API: `DATABASE_URL`, the Ed25519 public key, `ADMIN_SUBJECTS`, and the `blog-media` S3 settings. Examples are `deploy/prod/*.env.example`.
- `/srv/blog/web.env` is Next.js: `API_URL=http://api:8080`, `SITE_URL`, `SITE_INDEXING`, Better Auth, the production GitHub OAuth app, the GitHub id, and the Ed25519 private key.
- `/srv/blog/postgres.env` is the database user, password, and database name. The password is the one inside `DATABASE_URL`.
- `/srv/blog/caddy.env` is `DOMAIN`, the apex name with no scheme.
- `/srv/blog/backup.env` is the token scoped to `blog-backups`.
- `/srv/blog/.env` is only `IMAGE_TAG`. The deploy workflow rewrites it.

A push to `main` runs CI. When that push's CI run succeeds, `.github/workflows/deploy.yml` runs. A pull request does not deploy, even from a branch named `main`. CI does not cancel a push to `main`, so a slower run can finish last; that deploy is skipped when its commit is no longer the tip of `main`. A manual run can still deploy an older SHA. The workflow builds `ghcr.io/elmerred09/blog-api`, `blog-migrate`, and `blog-web` tagged with the commit SHA. `SITE_URL` is the repository variable. `SITE_INDEXING` is `false` until that variable's job is changed and a new image is built. The droplet must already be logged in to GHCR with a `read:packages` token (`docker login ghcr.io` as `deploy`). The workflow SSHes as `deploy` and runs `docker compose --profile tools pull`. Caddy and Postgres are pinned by digest in `deploy/prod/compose.yaml`, so that pull does not upgrade them. It then runs `docker compose --profile tools run --rm migrate up </dev/null`, then `docker compose up -d`. The stdin redirect matters: `compose run` would otherwise read the rest of the script and the job would still exit 0. After the smoke check it runs `docker image prune -af --filter "until=168h"`; images in use stay, and a rollback builds that SHA from GHCR again. Each Compose service caps json-file logs at 10 MB times 3 files. The `tools` profile is what makes the one-shot migrate service available. GitHub secrets for that SSH are `DEPLOY_HOST`, `DEPLOY_SSH_KEY` (a key whose public half is in `deploy`'s `authorized_keys`, separate from a personal key), and `DEPLOY_KNOWN_HOSTS` (`ssh-keyscan` of the droplet).

To roll back, run the Deploy workflow and pass the older commit SHA. That builds and starts that commit. `migrate up` runs again and does not reverse a migration. Migrating down is a separate, deliberate `docker compose --profile tools run --rm migrate down`.

`deploy/prod/backup.sh` runs `pg_dump -Fc` in the Postgres container, reads the archive back with `pg_restore` before uploading, and uploads `blog-YYYYMMDD.dump`. A dump that dies partway is not uploaded, so it cannot replace an earlier good dump from the same day. Dumps dated before 14 days ago are deleted. Install the timer once, as root:

```bash
sudo cp /srv/blog/blog-backup.service /srv/blog/blog-backup.timer /etc/systemd/system/
sudo systemctl enable --now blog-backup.timer
```

Prove a backup by running `/srv/blog/backup.sh`, then restoring the dump into a scratch database. Point-in-time recovery is not set up.

OpenTelemetry stays off in production until `OTEL_*` is set. Indexing stays off until `SITE_INDEXING=true` is baked into a new web image.

## Working modes

- **Human writes, agent reviews and teaches:** SQL, search ranking, and Postgres tuning. Explain, critique, or quiz; don't generate the implementation unless asked.
- **Agent writes, human reviews:** boilerplate such as Next.js scaffolding, CI YAML, Makefile, Docker config.
- For a new feature: plan first, write tests, then implement.
